# Find-Engine

> Find-Engine 是 [duiye](https://github.com/LZY0105/duiye) 软件使用的题目与答案匹配模型。

[English](README.md) | [简体中文](README.zh-CN.md)

把习题册中的题目与另一本答案册里的答案对应起来，让正在阅读教材的学生能直接看到眼前题目的答案。

面对两份 PDF，除书中印刷内容外没有任何共享标识符，本引擎会判断每条答案究竟属于哪道题——或者拒绝作答。

纯 JavaScript、核心零运行时依赖、无需网络。项目从一款 Android 数学学习平板应用中抽离出来，并完全在设备端运行。公开 PDF 演示使用仅限开发环境的 PDF.js 适配器，`src/` 下的核心引擎仍然零依赖。

> **📄 [研究报告](RESEARCH-REPORT.md)** — 包含完整的设计依据、评测方法、消融实验、参数扫描，以及五个有记录的负面结果。下文只是摘要，详细内容以报告为准。

## 问题背景

题号会在每章重新开始，因此一本书中可能有多个“12”。内容信息很稀薄——一条答案条目往往只给出结果。题目之间的文字表述也高度相似：在一页求导习题中，每道题几乎都是“求函数……的导数”，所以整串文本相似度无法区分它们。

所有问题之下还有一条根本原则：**错配比不匹配更糟。** 缺少答案只是带来不便；错误答案却会以与正确答案同样的权威性呈现，学生无法察觉，后续系统也会自信地把原本正确的作答判断为错误。

## 工作原理

输入两份文档。在匹配任何一道题之前，引擎先决定自己是否愿意处理这两本书。

### 门控，按顺序

| 门控 | 判断什么 | 未通过时 |
|---|---|---|
| **角色** | 左边是习题册、右边是答案册吗？ | `BLOCKED` |
| **同一性** | 这是同一本书吗——年份、科目、抽样内容锚点？ | `BLOCKED`；若只是证据缺失，则为 `UNKNOWN_PAIR` |
| **文本层质量** | 文本层是否真正覆盖了这份文档？ | `OCR_REQUIRED` |
| **结构** | 哪些书签是题目，而不是章节？ | 无题目级索引；仅保留区域定位 |

这些结论**由引擎自行推导，绝不由调用方提供**。这正是关键所在：早期版本曾把 `exactId`、`sectionAligned`、`pairStatus` 当作参数接收，在全部 60 种“错书 / 错角色”组合上实测，有 52 种会给出自信的答案。现在是 **0 / 60**。

### 然后是级联，从最便宜的信号开始

一道题一旦被某个阶段解决，后续阶段便不再运行。

| 阶段 | 信号 | 解决的问题 |
|---|---|---|
| **0** | PDF 书签树中的层级题号 | 同一题号在两本书中都只出现一次 |
| **1** | 单调且感知层级的目录对齐 | 把范围缩小到答案册中的一个章节 |
| **2** | 结合运算符上下文的数学加权相似度 | 题号重复或缺失 |
| **3** | 有界 Needleman–Wunsch 对齐 | 内容信息稀薄时，利用位置顺序 |

在 2023 年语料上，508 道题全部在**阶段 0**解决：标识符本身就是答案，因此完全不需要内容比较。

**运算符上下文**是其中最不直观的一环。二元组相似度本质上是一个“袋”：它统计哪些字符对出现过，却不关心它们出现在哪里。`x^2+3x` 与 `x^3+5x` 的区别集中在运算符周围，因此引擎会锚定每个运算符，并分别向左右取三个字符的窗口：

```text
x^2+3x   ->   "··x^2+3"   "x^2+3x·"
x^3+5x   ->   "··x^3+5"   "x^3+5x·"
```

两个标记均不相同，而普通二元组袋仍会共享 `x^`、`+` 和 `x`。窗口半径 3 来自实测而非惯例：区分裕量在 3 处达到峰值，增至 6 时甚至有一组样本的排序发生反转。[完整扫描见研究报告](RESEARCH-REPORT.md#61-operator-context-window-radius)。

![运算符上下文窗口半径与区分裕量](figures/radius-sweep.svg)

## 五种答复，而不是两种

拒绝**作答**不应等于拒绝**帮忙**。引擎会返回五种结论之一，其中只有第一种可能以那种真正代价高昂的方式出错。

| 等级 | 含义 | 会以高代价方式出错吗？ |
|---|---|---|
| `AUTO_MATCH` | 这条答案就是本题的答案 | **会**——其余一切都是为了保护它 |
| `REVIEW` | 答案在这几条之中 | 不会——它并未断言选择 |
| `LOCATED` | 答案在这几页里 | 不会——这是范围，不是身份 |
| `REFUSED` | 证据不足，无可奉告 | 不会 |
| `BLOCKED` | 这两本书根本不该放在一起 | 不会 |

等级是**上限，而不是目标**：任何结果都不得为了让覆盖率数字好看而被提升。`matched` 跟随等级取值，因此低置信度的猜测再也无法作为最终答案抵达读者。

配对状态决定哪些等级可用。未经验证的配对仍可定位、仍可给出候选，只是不能作答：

| 配对状态 | `AUTO_MATCH` | `REVIEW` | `LOCATED` |
|---|---|---|---|
| `VERIFIED_PAIR` | ✅ | ✅ | ✅ |
| `UNKNOWN_PAIR` | ❌ | ✅ | ✅ |
| `REJECTED_PAIR` | ❌ | ❌ | ❌ |

当重复题号没有章节对齐时，引擎会**拒绝匹配，绝不依靠位置强行决定**。对齐算法总能给出某种分配；直接接受它，就会把真实歧义变成自信的错误答案。

## 结果

共八份文档：三组两侧都有书签的“习题册 / 答案册”配对，以及一组扫描件配对。所有数据均基于整本书，没有任何抽样。

### 安全性

| | |
|---|---|
| 测试的错书 / 错角色组合数 | **60** |
| 产生任何自动答案的组合 | **0** |
| 在文档层面被拦截 | 53 / 60 |
| 其余 | 停留在 `UNKNOWN_PAIR`，该状态无法自动作答 |

覆盖了错年份、错科目、答案↔答案、习题↔习题以及正反颠倒等情形。**全部通过公开接口测量**——测试内部辅助函数并不能说明调用方是否可以绕过门控。

### 能力

| 配对 | 已解决 | 错误 | 单页 p95 |
|---|---|---|---|
| 2023 | **508 / 508** | **0** | 1 ms |
| 2024 数学分析 | **271 / 271** | **0** | 2 ms |
| 2024 高等代数 | **217 / 217** | **0** | 1 ms |

以上为标定（calibrated）公式策略下的结果。在严格（strict）策略下——题目中每个完整表达式都必须在答案中找到对应——同样三组配对分别解决 470、159、175 道，**错误仍为 0**。该规则牺牲召回率，而在本语料上并未带来可测量的精确率提升，因此默认启用但可切换，两个分支都在测试套件中被覆盖。参见 `FORMULA_POLICY`。

### 结构退化时

剥离书签树，再用由书签树构建的独立金标准评分：精确率从不下降，也不会仅仅因为缺少书签树就否决一组有效配对。召回率是向较低等级迁移，而不是消失。[消融方法与完整表格](RESEARCH-REPORT.md#5-evaluation)。

![四种组合中精确率保持 100%，拒绝率上升](figures/ablation-precision-refusal.svg)

无书签情形下的召回率，大部分由三项结构性识别贡献，其中没有一项是相似度阈值。答案册会印出自己的目录，导致正文解析把每个标识符都找到两次，并因此拒绝了本已定位的题目；书眉让互不相关的条目看起来相似；而在清除这两者之后——**印刷目录本身就是一份“标签→位置”索引**，恰恰就是缺失的书签树本该提供的东西。

读取目录需要知道印刷页码与 PDF 页序号之间的偏移量，而这个偏移是**从文档中恢复出来的，不是猜的**：凡是同时出现在目录与正文解析中的标签都可以投票，在 2023 年答案册上，508 个标签中有 492 个一致指向 +18。如果盲目套用这个偏移，会正确放置 492 个、错误放置 16 个；因此只有在两次独立读取彼此一致时才输出位置——而这恰好排除了那 16 个。

参见 `src/toc-filter.js`、`src/boilerplate.js`、`src/contents-index.js`。

## 扫描版书籍

扫描版习题册没有像样的文本层——这里的 2025 年分册在 465 页中只有 609 个字符，且仅分布在 0.7% 的页面上。引擎默认拒绝处理它，而 `tools/windows-ocr.mjs` 是一个可用的识别器，能让它变得可读：由 `pdftoppm` 渲染页面，`Windows.Media.Ocr` 负责识别。无需安装、无需联网，也没有任何一页离开设备。465 页耗时 6.7 分钟，零页失败——这是一项预处理作业，而不是让读者等待的即时操作。

识别会把文档从 `SPARSE_LAYER` 提升为 `USABLE`，并标记 `textOrigin: OCR`，同时索引出 607 道题——此前一道也没有。

**但这并不意味着这本书可以匹配了，该路径也尚未发布。**

仅有识别并不能解锁任何自动答案，也不应该解锁：引擎无法凭 OCR 得到的锚点验证两本书是否属于同一套，因此它只提供候选与页码定位，并保留答案不发。**绑定**——由用户明确表示“对，就是这两本”——补上了它无法自行确立的同一性，并会与两份文档的指纹校验，因此替换其中任一文件都会使绑定失效。

**绑定只确立“文档配对身份”，仅此而已。** 它不得把某一道题提升为高置信度。逐题验证——题目边界检测、完整公式覆盖、双向一致性、全局一一分配、足够的前二名裕量——仍然是必需的，而且尚未实现。

### 这些数字是什么，不是什么

绑定之后引擎会给出自动匹配，人们很容易把这个数量称作准确率。它不是。2025 年习题册没有题目级书签——这正是需要 OCR 的原因——因此没有任何独立信息能说明一道题**位于何处**。去检查“匹配到的答案是否落在该标签的答案区间内”几乎是循环论证：标签本身驱动了查找，结果自然按构造落在那里。本文件的早期版本正是在这个基础上报告了“178 正确、0 错误”。**该结论已被撤回。**

可以检查的是：标签是否印在它所匹配的那一页上，以及这些标签是否按书中的顺序排列。这些计数是**生成的，不是誊抄的**：

```bash
node tools/ocr-cache.mjs                        # 执行一次，约 7 分钟；PDF 需放在纯 ASCII 路径下
node tools/audit-ocr-matches.mjs                # 写出 reports/ocr-audit.json
node tools/audit-ocr-matches.mjs --allow-skip   # 在没有语料的检出中使用
```

**[reports/ocr-audit.json](reports/ocr-audit.json) 是唯一权威结果**，也正是审计脚本默认写出的文件——不存在第二个需要同步维护的文件名。撰写本文时，它记录了 178 次自动匹配事件，其中 100 次来自印有该标签的页面、78 次来自续页，8 个标签**只**出现在续页上，原始标签覆盖 108/573，按起始页对齐后为 100/573。对 8 组抽样配对的人工目视核查发现 7 对正确、1 对错误，因此错误率既不是零，目前也并不清楚。

两个脚本都不会假装。缓存构建器拒绝写出自己无法担保的缓存——它从 PDF 本身而非常量读取页数，并在出现以下任一情况时直接拒绝：有页面识别失败、有页面返回空白，或者中位页的文字量少到不像一次真正的识别。它写出的内容会附带源 PDF 的哈希与页数、识别器的设置与统计，以及生成它的提交号。审计脚本会把这些来源信息一路带入自己的产物，并在缓存自报不完整、或根本没有来源信息时在控制台发出警告——这样，来自部分识别的数字就不会被当成完整识别的数字来读。

审计脚本在输入缺失时还会**直接失败**，而不是为一次根本没发生的运行报告成功；`--allow-skip` 才是干净检出请求“通过”的方式。审计的推理逻辑本身位于 `src/ocr-audit.js`，并有单元测试覆盖，因此无需私有数据也能验证。

作为对照：同一本书在这项工作之前会产生 **479 个自信的错误答案**，因为它把 18 个章节书签当成了题目。拒绝作答已经好过这个结果；但它还算不上一项功能。

## 使用方法

只有一个入口。`preparePair` 掌管全部门控；除它之外，没有任何东西能产生匹配。

```js
import { preparePair } from './src/matching-engine.js';

const prepared = await preparePair({
  exerciseDocument,           // DocumentAdapter
  answerDocument,             // DocumentAdapter
  recognizer,                 // 可选；扫描版书籍必需
  binding,                    // 可选；用户已确认过的配对
  expectScript: 'han',
});

if (prepared.status === 'REJECTED_PAIR') {
  // 错书、错角色、错年份。如实告知，不要匹配。
  return prepared.decision.reasonCodes;
}

const matches = await prepared.session.matchQuestion({ page, region });

for (const m of matches) {
  switch (m.rung) {
    case 'AUTO_MATCH': show(m.entry.answer); break;
    case 'REVIEW':     offer(m.candidates); break;
    case 'LOCATED':    say(`答案位于第 ${m.region.from}–${m.region.to} 页`); break;
    default:           explain(m.cappedBy, m.reasonCodes);
  }
}
```

一次处理整本书：`await prepared.session.matchAll()`。

**不允许跨越该接口传入的内容**：`exactId`、`sectionAligned`、`crossBookComparable`、`pairStatus`，以及任何断言“某事已被验证”的布尔值。它们都是结论，而得出结论正是本模块自己的职责。

`expectScript: 'han'` 告诉质量门控这应当是一本中文书，从而发现仅靠噪声比例无法识别的阅读器配置错误。

### 文档接口

引擎本身不读取 PDF。调用方需要提供满足下列接口的任意对象：

```js
{
  numPages: number,
  outline: { available: boolean, items: [{ title, pageNumber, depth, children }] },
  async extractText({ from, to }): Array<{ page: number, text: string }>,
}
```

文本行还可以额外携带 `y` 与 `height`。携带时，`region` 会选中被点击的那道题，而不是整页；不携带时，结果会明确返回 `regionApplied: false`，而不是悄悄把整页都返回。

### 识别器接口

对扫描版书籍，请提供 `recognizer(page) => Promise<string>`。引擎会调用它，并且**只有识别成功才能解除 `OCR_REQUIRED`**——如果识别器返回空、抛出异常，或产出的文本层依然过于稀疏，文档将保持“失败即拒绝”的状态。

`tools/windows-ocr.mjs` 是一个可用的参考实现，完全基于 Windows 已有的能力构建——`pdftoppm` 负责渲染，`Windows.Media.Ocr` 负责识别——因此无需安装、无需联网，也没有任何一页离开设备。

### 可识别的编号形式

`1.`、`12)`、`15、`、`第 9 题`、`3．`，以及层级形式 `1.1`、`1.200`、`2.231`、`例题 1.31`；编号必须锚定在行首。`(7)`、`（8）` 被视为当前题目的**小问**，绝不会单独建立题目。


大多数测试关注的是如何**拒绝**，而不是如何匹配；主要测试面是公开接口：一个伸进内部实现的测试套件，无法说明调用方是否能够绕过门控。

正确性由两个**不共享失败模式**的金标准交叉检验——两棵书签树，以及答案正文中自己印出的标签。二者之间的**矛盾**会被绝对判为失败；而**沉默**只在其实测比例内被容忍。

真实 PDF 测试需要一份从原书提取的文本语料，该语料**不会提交**到仓库——它来自受版权保护的书籍。`tools/extract-corpus.mjs` 可重新生成：通过 `FIND_ENGINE_CORPUS` 指定结果路径，或把结果放在仓库旁的 `../find-engine-corpus/`。语料不存在时，相关测试会跳过而不是失败，因此新克隆的仓库仍能通过测试。

## 复用前应了解的两件事

**位置回退已经实现，但默认关闭。** 对真正平行的文档配对，它可以达到 100% 精确率；对不平行的配对，精确率为 0%，会把 120/120 道题全部以 `MEDIUM` 置信度错误返回。无法判断自身何时不适用的信号，无法遵守“错配比不匹配更糟”的原则。[测量数据](RESEARCH-REPORT.md#71-a-positional-prior-that-fails-silently)。

**遇到 `OPAQUE` 时，先怀疑阅读器，再怀疑文档。** 最初被认为是嵌入字体损坏的案例，最终发现是 pdf.js 缺少 CMap 文件。[这次误判的代价与所得经验](RESEARCH-REPORT.md#72-a-confident-misdiagnosis)。

## 相关工作

对齐机制本身是标准方法，包括动态规划、单调对齐和相似度评分。本项目的特殊性来自其应用领域：层级题号、书签锚定、数学结构加权，以及有意设计的拒绝权。研究报告中给出了与 Gale–Church、Hunalign、Bleualign、Maligna、Vecalign 和 Bitextor 的[对比定位](RESEARCH-REPORT.md#2-related-work)。

## 局限性

- 答案册顺序被打乱时召回率会下降。对齐是单调的，目前还没有全局非单调分配，因此交叉情形被拒绝，而不是被解开。
- 双向一致性与有界 Top-K 检索尚未实现。受此影响，2024 年退化组合的单页耗时约为 0.7–1.6 秒。
- 置信度是序数等级，而非标定过的概率。在积累到足够多的独立书籍配对、能够诚实标定之前，它会一直如此。
- 二元组相似度与语言无关，但不具备语义理解能力。
- Android 性能尚未测量，所有数据都来自桌面环境。
- 参数针对中文数学教材调优。方法可以推广，常数不能直接照搬。

报告中还列出了[有效性威胁](RESEARCH-REPORT.md#8-threats-to-validity)。
