# Android 匹配引擎优化方案：复审版

日期：2026-09-14。状态：方案审查与修订完成；尚未实施优化、构建新包或验证性能收益。原方案保留，本版为后续实施依据。

## 结论与证据范围

原方案方向正确，但有影响正确性、内存与交付的缺口，不能称为“完美”。保留“先优化 JavaScript，再决定是否局部 C++”的路线，先通过评分等价验证，再接入后台执行。

仍沿用用户认可的 2026-09-13 真机基线：新进程首次查询 9048.9 ms，最长主线程任务 4905 ms；10 次热查询 7.2–22.9 ms，中位数 9.05 ms；5 页热查询 16.2–19.8 ms。冷查询主要样本只有 1 次，CPU profile 来自另一次运行，不能直接相减预测收益。两进程总 PSS 约 440 MiB 的读数不等于引擎独占内存。

用户说明后续版本只改动画，本次未重测平板。源码专项审查确认：独立引擎 HEAD 为 931792f2217a7bb351e3794f27e590c494f68cae；Android 本地 HEAD 为 19653e426105ec528430fdcef517fa315a6c6312，受版本控制的工作区干净。Android 相关索引已刷新；独立引擎补充了直接调用当前导出函数的运行验证，索引工具的 Git 外部校验仍返回 git_unavailable，不能将缓存校验当成额外 Git 证明。

原始证据：[真机性能评估报告](真机性能评估报告.md)。后续性能测试应记录实际构建提交和 APK 资产身份，不能把当前本地源码等同于之前受测安装包。

## 1. 复审发现及处理

| 优先级 | 原方案缺口 | 本版要求 |
|---|---|---|
| 必须先修订 | “一次标准化”可能改变原分数 | 按原有分支与阶段缓存，保留转换顺序和次数 |
| 必须先修订 | 共享特征中的计数可能被评分修改 | 缓存特征只读，比较使用独立临时计数或无修改实现 |
| 必须先修订 | Worker 数据裁剪可能改变配对证据 | 显式输入契约；传输前后比较完整判定与证据 |

原方案已正确要求保留候选顺序与同分第一项，本轮为这些要求补充边界用例，不把它们重复列为原方案错误。

## 2. 第一阶段：准确地复用文本特征

### 2.1 已验证的反例

设 N 为现有 normalizeForMatch。直接调用当前模块得到：

- a = “x\ left+y”，b = “x+y”。
- N(a) = “x\left+y”，N(N(a)) = “x+y”。
- 原始 contentSimilarity(a,b) = 0.8055555555555556。
- 先标准化再调用旧入口，分数变为 1。

因此 N 不幂等，不能把一段统一标准化后的文本交回原入口，或者把原有各分支都改成只标准化一次。

另一个反例：a=b=“\ left”，原散文分数为 1，数学分数为 0，符号上下文为 null，总分为 0.25。数学的 0 不能误当成“没有数学信息”。当前代码没有 NFKC；“Ａ+Ｂ”对“A+B”的原总分为 0，不得在性能改动中顺便加入兼容规范化。

### 2.2 特征契约

每段原始文本、每个确定的预处理阶段只计算一次，保留以下路径：

- 散文：P=N(t)，从 P 构造 bigram 及计数总数。
- 数学：F=extractMathFragments(t).join(' ')；抽取内部已执行 N。数学评分使用 N(F)，但数学是否可用必须根据原 F 是否为空判断。
- 符号上下文：从 N(t) 生成。任一侧少于 2 个运算符锚点时返回 null，按现有规则回退。
- 分数计算仍按现有权重和运算顺序执行。null、0、空字符串、原始文本的真值不能混用。

当前 diceMultiset 会递减其局部计数 Map。若把这份 Map 放入共享特征后直接复用，前一次比较会改变下一次的输入。缓存的数组/Map 应按只读合同使用；比较函数采用不修改缓存的方式，或创建独立工作计数。只对外层对象调用 Object.freeze 并不能代替 Map 不被修改的实现约束。

保留 contentSimilarity(a,b) 既有调用方式，优化入口在内部使用相同特征合同。为差分保留固定基线实现/固定基线提交，避免新旧入口最终调用同一份已修改代码而形成无效对照。

### 2.3 分批算法

实际抽样题数 S 不超过现有配置，候选数为 N。保持原抽样顺序与候选顺序，各题保留最佳项；只用严格大于号更新。按原顺序处理候选批次，复用同一候选特征服务全部抽样题。

比较仍有 S×N 次；被复用的是各阶段文本预处理，不宣称整个算法成为线性。对常见规模可先缓存抽样题特征、逐个构造候选特征；若批处理需要可再测每批 128 条，128 只是调参起点，不是正确性条件。

来源：[question-matcher.js](https://github.com/LZY0105/Math-answer-to-question-matching-model/blob/931792f2217a7bb351e3794f27e590c494f68cae/src/question-matcher.js#L79)、[symbol-context.js](https://github.com/LZY0105/Math-answer-to-question-matching-model/blob/931792f2217a7bb351e3794f27e590c494f68cae/src/symbol-context.js#L61)、[contentAnchorAgreement](https://github.com/LZY0105/Math-answer-to-question-matching-model/blob/931792f2217a7bb351e3794f27e590c494f68cae/src/pair-verifier.js#L203)。

## 3. 第二阶段：后台执行与文档生命周期一起接通

### 3.1 先定义验证输入，保持原有证据

首版仅将配对准备中的重计算放入专用 Worker，热查询继续走现有快路径；不为了预留 C++ 提前重构整个查询接口。

当前 verifyPair 无手动绑定路径所需输入至少包含：

- 双方索引的 source，以及保持原序和原始值的 entries[].label/text。
- 文档 outline.items 中用于判断的递归 title/children。
- doc.lines 的既有语义：年份判断最多前 4000 行，学科最多前 3000 行。

不能丢掉 source，否则可能失去 OUTLINE 证据；不能把 index.lines 填成原文档本来不存在的 doc.lines。缺失、空数组和有内容的字段按原行为保留，不能为了“补全”而改变输入。

当前 UI 不传 manualBinding；“已关联答案册”不得直接当作手动授权而绕过验证。如果未来支持 manualBinding，需扩展独立输入版本：fingerprintDocument 还会读取 numPages、目录及全体行的分散采样，不能继续仅截前 4000 行。

定义显式序列化数据结构，发送普通数据与必要的专用缓冲区，返回判定、reasonCodes 与 evidence。PDF 实例、方法、闭包和 UI 对象不进入消息。结构化克隆不支持函数且不保留普通对象的原型链，不能把对象直接存取当作完整功能恢复。[MDN：结构化克隆](https://developer.mozilla.org/en-US/docs/Web/API/Web_Workers_API/Structured_clone_algorithm)

来源：[Android pair-verifier.js](https://github.com/LZY0105/duiye/blob/19653e426105ec528430fdcef517fa315a6c6312/src/pdf/pair-verifier.js#L149)、[fingerprintDocument](https://github.com/LZY0105/duiye/blob/19653e426105ec528430fdcef517fa315a6c6312/src/pdf/fingerprint.js#L45)。

### 3.2 共享打开任务和准备任务

当前 _backgroundAnswer 在 openStoredDocument、getOutline 两次等待后才写入 Map；现有清理只能处理已登记的对象。这意味着并发打开可生成重复实例，关闭期间尚未完成的实例也可能迟到后重新入 Map。

应按“答案资源身份＋内容版本”立即登记进行中的打开 Promise，复用同一打开过程。成功时再次校验资源代际；已删除、失效或没有消费者的迟到实例执行销毁。失败或取消后清除进行中状态，不能缓存一个永久失败的 Promise。

相同书籍组合共享准备任务。准备会话的配对键包含双方内容版本和配置版本；页面请求另外携带消费者、请求编号与页码。页码不应成为配对准备缓存键，否则翻页会反复准备。

### 3.3 取消、失效及失败

- 关闭一个面板先撤销该消费者；有其他消费者时保留共享任务。最后一个消费者离开时，按预热策略取消或保留，策略必须显式。
- _invalidatePairCaches 触发时，先推进组合版本并解绑/取消旧任务，再按实际引用回收 PDF 句柄。清空 Map 不等于取消正在进行的异步工作。
- 所有 await 之后以及写回缓存、写入磁盘、渲染结果之前，校验资源版本与请求身份；swap、换书、换关联、删除、销毁都要覆盖。
- Worker 以有限批次执行，并通过真正让出事件循环处理取消；仅 await 已完成的 Promise 不能保证取消消息得到处理。
- Worker 初始化失败、运行异常、messageerror、超时或进程丢失，都必须让等待方结束，清除任务引用与定时器，并允许重新发起。重试次数有上限，不形成自动重启循环。
- terminate 会立即终止整个 Worker，因此不能因为一个消费者取消，就销毁其他消费者仍需要的共享计算。[MDN：terminate](https://developer.mozilla.org/en-US/docs/Web/API/Worker/terminate)

首版建议每个工作区只运行一个匹配 Worker，一次执行一个准备任务；待处理队列最多保留两个不同的当前组合，合并同组合请求，移除过期请求。传输按确认后再发下一批的方式限制在途数据，不能把全部分批消息一次排入队列。

来源：[_backgroundAnswer](https://github.com/LZY0105/duiye/blob/19653e426105ec528430fdcef517fa315a6c6312/src/pdf/pdf-workspace.js#L3307)、[_invalidatePairCaches](https://github.com/LZY0105/duiye/blob/19653e426105ec528430fdcef517fa315a6c6312/src/pdf/pdf-workspace.js#L2034)、[_releaseAnswerHandles](https://github.com/LZY0105/duiye/blob/19653e426105ec528430fdcef517fa315a6c6312/src/pdf/pdf-workspace.js#L3331)。

## 4. 内存预算的真实边界

预算要同时覆盖抽样题特征、当前候选特征、临时计数、消息在途数据、主线程与 Worker 的重复数据。不能只看候选条数或查询结束后的 JS 堆。

现有预处理会一次处理完整文本。首版选择保持精确语义的逐条/有限批处理：单条超大时允许独立处理，但必须记录该单条造成的额外峰值；抽样题缓存过大时可缩小题目分组，以必要的重复计算换取更低同时保留量。不得截断、丢弃超长候选并声称结果等价。

因此首版保证消除无界队列与长期特征缓存，不保证任意长度输入固定内存。如果产品要求严格硬上限，必须另立工作实现精确流式处理，维护标准化状态、bigram 跨段字符和符号上下文边界；不能对任意切片各自调用旧函数便宣称等价。若选择对超限输入拒绝处理，那是新增产品行为，应单独决策和验收。

从第一包起测内存，重点记录传输和构造时的峰值、完成后的稳态、撤销任务和换书后的对象保留。PSS 采样只能给采样分辨率内的峰值估计，JS 堆、外部缓冲区和 PDF/图形占用需分别观察。先验证回收路径，再为真正占用大的类别确定下降目标。

## 5. 第三阶段：跨进程缓存，按收益决定是否实施

现有会话缓存有效，先完成前两阶段并测量剩余耗时，再决定持久化索引、目录对齐和验证证据是否值得投入。

- 缓存键绑定双方内容身份、索引/证据格式版本、文本提取配置、算法/策略版本和绑定状态；不能只用文件名。
- 分别实现序列化与还原，不序列化可执行方法。恢复后使用现有模块重建查询能力，并做完整行为对照。
- 写入先完成计算与序列化，再提交数据及完成标记。多批大记录采用新版本数据＋最后一次原子切换有效清单；读取只接收完整一致版本。
- 若采用 IndexedDB，以事务 complete 确认提交，不把单个 put 的 success 当成整份缓存完成；未完成写入、配额不足、数据损坏均按缓存未命中处理，可重建数据的写入失败不应使匹配失败。[MDN：事务提交](https://developer.mozilla.org/en-US/docs/Web/API/IDBTransaction/complete_event)
- 原文件删除、内容变化、答案关联变化或配置变化时失效；旧异步任务不得重新写入已失效版本。清缓存只删除可重建记录。
- 预热限于当前组合、首屏完成后的空闲时间，前台查询优先，不扫描整座书库。

## 6. 从独立引擎到 Android 的交付链

当前应用相对导入自身 src/pdf/question-matcher.js、src/pdf/pair-verifier.js；独立引擎 src 下的修改不会自动进入应用。现有 build:android 只执行前端构建与 Capacitor 同步。

实施前登记纯算法的权威来源、同步文件清单、提交标识，以及 Android 必须保留的适配差异。同步目标是共享算法文件及新增依赖，不能整目录覆盖应用的 PDF 适配与生命周期逻辑。

每个涉及算法的改动包必须完成：独立引擎差分 → 同步应用副本 → 应用集成差分 → 前端构建和 Android 资产同步 → 构建 APK → 核对 APK 内算法资产及版本 → 真机验收。保留可以分别回滚的改动；只有独立仓库测试通过不算端侧优化交付。

## 7. 验收合同

### 正确性：先通过，才比较性能

比较单对分数、anchors.top1/sampled/shared/sufficient、完整 pair status/reasonCodes/evidence，以及最终题号、页码、分级和拒答原因。固定版本和配置下，第一阶段要求未解释的差异为零。新旧实现不能复用同一份会被修改的特征数据。

必须覆盖本版两个非幂等/空数学反例、全角字母、同一特征重复评分和候选遍历顺序变化、全零同分、128/129 批次交界、公式冲突和错误答案册。

原始 e.text 的真值也需保留：空白字符串在现行为中仍参与。已验证一个 8 道空白题且答案首项为第 8 题的样例，原 anchors 为 top1=0.125、sampled=8、shared=8、sufficient=true；若丢弃标准化后空文本，会变为 top1=null、sampled=0、shared=0、sufficient=false。这说明只比较最终页面不足以发现证据变化。

生命周期补测：两个消费者共享后取消其中一个、同答案册并发打开、打开未完成时关闭/删除、换书后旧消息到达、Worker 失败后重试、缓存写入中途停止。无书签与扫描件另列结果，不能沿用有书签资料的性能与准确性结论。

### 性能：目标而非承诺

| 场景 | 建议目标及口径 |
|---|---|
| 原资料首次准备未命中 | 首轮中位数不高于 5 秒；3 秒为进一步目标，不保证只优化验证就能达到 |
| 配对验证 | 单独计时目标中位数不高于 1 秒；传输、排队与初始化另记 |
| 已准备查询 | 初步 30 次作冒烟；正式至少 100 次覆盖 5 页，报告总体及分页面分布，样本 p95 目标不高于 50 ms |
| 跨进程缓存命中 | 已恢复书籍后的首次查询目标不高于 1 秒；应用启动和 PDF 恢复另列 |
| 主线程 | 记录匹配引入的 50 ms 及以上任务，目标为零；加载状态可见目标 100 ms 内 |
| 内存 | 队列、在途批次和资源引用受控；报告超长单条峰值与反复换书后的保留对象，不作任意输入固定占用承诺 |

冷查询后续至少 5 次独立进程运行，记录全部值、中位数、最慢值及成功/失败数，不声称稳定 p95。100 次热查询的 p95 也只是该测试样本的统计，不代表所有设备和资料。

原基线是点击到结果 DOM 完成；修订后继续保留同口径，同时另测用户输入响应与可见结果。50 ms 是 Long Tasks 的观测门槛，不是动画帧预算；没有长任务不能证明动画流畅。帧/绘制指标、UI 并发阅读需独立观察。[MDN：长任务](https://developer.mozilla.org/en-US/docs/Web/API/PerformanceLongTaskTiming)

性能计时关闭 Profiler，热点采样另跑；固定书籍、页面、缩放、缓存状态及构建类型，记录电量与温度。调试包不能直接与发布包混比并把全部差值归于算法。设备本次不重测；正式实施后的比较使用相同条件的新旧构建，原数据继续作为诊断基线。

## 8. 改动顺序与 C++ 决策

1. 固定输入/版本、加入分阶段计时和上述反例，确认应用副本同步清单；内存观察从此开始。
2. 仅改特征复用与只读评分，完成引擎和应用两侧差分及端侧测量。
3. 修复后台答案打开的共享与迟到释放，再接 Worker、消费者取消和有界传输，验证 UI 响应及峰值内存。
4. 按剩余耗时决定持久化与预热；针对内存归因结果调整 PDF、索引和句柄回收。
5. 若仍未达目标，再决定局部 C++ 原型。

C++ 触发条件应覆盖两类需求：新的 profile 显示纯评分仍是主要时间成本；或者证据显示匹配特征/索引确实占据主要可节省内存，且 JS 数据布局及生命周期优化仍不够。若主要成本在 PDF 解码/渲染或数据复制，就处理相应位置。

原型用批量接口，保留 Unicode、null、浮点与同分语义，比较应用端到端耗时、峰值/稳态内存、安装包与维护成本。时间导向可讨论相对已优化 JS 再提升约 30% 的门槛；内存导向应根据归因后的绝对节省量设目标，不能强行套用提速百分比。以上都是决策建议，尚无 C++ 收益实测。
