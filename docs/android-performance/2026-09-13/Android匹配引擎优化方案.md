# Android 匹配引擎优化方案

日期：2026-09-14。范围：Android 离线查询速度、界面响应及内存；本轮只交付方案，未修改应用或引擎源码。

## 决策与依据

先做 JavaScript 特征复用、后台执行及资源回收，再根据结果决定是否开发局部 C++ 内核。

沿用用户认可的 2026-09-13 真机数据。测试包为当日 21:25:35 安装的 1.4.0 调试包；用户说明后续版本只改动画，因此本方案继续采用原数据定位匹配计算瓶颈。这不代表重新测量了新版动画、图形内存或帧率。

| 已有实测 | 结果 | 对方案的意义 |
|---|---:|---|
| 新进程首次查询 | 9048.9 ms，1 次 | 优先缩短首次准备 |
| 首次查询最长主线程任务 | 4905 ms | 必须消除长时间界面阻塞 |
| 同页重复查询 | 7.2–22.9 ms，10 次；中位数 9.05 ms | 保持现有热查询速度 |
| 已准备状态下查询 5 个页面 | 16.2–19.8 ms | 无须先重写日常查询 |
| 配对验证调用链 | 非空闲 CPU 采样约 72.5% | 先处理验证内的重复文本计算 |
| 两进程总 PSS，十次热查询前后 | 443.6 → 432.4 MiB | 不能据此认定引擎泄漏或承诺原生化节省量 |

CPU 采样与主要冷查询来自不同运行，调用链时间相互嵌套；不能把各项相加，或把某函数采样时间直接从 9 秒中扣除预测优化结果。原报告和原始数据见 [真机性能评估报告](真机性能评估报告.md)。

## 1. 先减少重复计算：收益最明确的一步

主要位置：独立引擎 src/question-matcher.js 的 contentSimilarity、similarity、normalizeForMatch、bigrams，以及 src/pair-verifier.js 的 contentAnchorAgreement。

当前验证最多抽样 24 道题，与全部非空答案候选比较。每次比较都会重新构造文本特征。改为：

1. 对实际选中的抽样题目，各提取一次标准化文本、二元组及数量、数学片段与符号上下文。
2. 按原顺序分批读取答案候选，初始每批 128 条；每条答案只构造一次特征，供全部抽样题目复用。
3. 为每道抽样题保留当前最佳分数及候选；处理完一批即释放该批特征。超长答案同时受文本量预算约束，不能只按条数限流。
4. 完成验证后释放临时特征，保留现有配对判定。首版不增加全书永久特征缓存。

设抽样题数为 S、候选数为 N：比较仍是 S×N 次；每一类可复用的文本预处理降为约 S+N 份。这个变化减少的是重复预处理，不是把整个算法变为线性，也不保证固定倍数的端到端加速。

建议在引擎内部增加文本特征构建与特征评分函数，保留现有 contentSimilarity(a, b) 的调用方式，使其他调用者无需同步迁移。二元组总数在构造时计算，避免每次评分再生成 values 数组求和。

一致性要求：保持抽样位置、候选顺序、空文本和短文本处理、Unicode 行为、公式权重、分数及同分时选择第一项的规则。只复用与单段文本有关的中间结果；与两段文本共同有关的比较仍需逐对计算。不得靠减少验证样本、跳过候选、放宽阈值获取性能提升。

交付：可独立回滚的特征复用改动、相同输入的新旧结果差分、首次验证时间和临时内存对照。

## 2. 把首次计算移到后台，解决卡顿

接入位置：Android 应用 src/pdf/pdf-workspace.js 的 PdfWorkspace.showAnswersForPage。现有应用已经缓存 questionIndex、answerIndex、outlineAlignment、answerComparability、pairVerdict；继续利用这些状态，新增“准备中”的任务复用，避免用户连点时启动重复准备。

先把配对验证移入一个专用 Worker，并以实测确定后续需要迁入的索引构建或批量匹配步骤。PDF 读取和渲染保持现有所有权：PDF 文档对象不能直接当作普通消息发送，也不应为匹配再打开一套完整 PDF 实例。

为页面提供小而完整的异步会话接口，负责准备、查询和释放；阶段一只接通后台准备，其余流程继续调用现有实现。接口内部集中处理缓存身份、重复请求、失败和资源回收，不把这些规则分散到按钮处理函数。

必须落实：

- 同一书籍组合共享进行中的准备任务；查询消息带任务编号、书籍组合版本和请求页码。
- 换书、换答案关联或关闭面板后，过期结果不得覆盖当前页面。
- 真正的取消必须能停止计算：在候选批次间让出 Worker 事件循环并检查取消状态；仅发送取消消息无法打断一个持续运行的同步循环。取消专用任务时也可销毁 Worker。
- 首次传入验证必需的数据，避免每次查询复制全文和完整索引。先按字段裁剪与分批传递；后续若采用专用 ArrayBuffer，可转移所有权，不能转移渲染器仍在使用的缓冲区。
- 后台失败时显示可重试状态；不能以跳过配对验证作为降级方式。
- 主线程及时显示准备状态，允许继续阅读。只加 async、Promise 或延迟调用不会让同步计算自动离开主线程。

Worker 能把计算移出界面线程；普通消息数据可能发生复制，转移 ArrayBuffer 则会让发送方失去该缓冲区的使用权。因此必须同时核对线程间传输成本与内存。[MDN：使用 Web Workers](https://developer.mozilla.org/en-US/docs/Web/API/Web_Workers_API/Using_web_workers)

交付：后台准备、取消及过期结果处理、任务复用、主线程长任务和两进程内存对照。

## 3. 改善再次打开：有条件地持久化准备结果

这是第二轮投入，先完成前两项并确认剩余时间分布。当前会话缓存已经有效；本步骤补的是跨进程复用，不是重复增加会话缓存。

- 本地持久化可序列化的索引、目录对齐结果及配对证据；不要存活的 PDF 对象或 Worker 对象。
- 缓存键包含双方文档身份与内容版本、引擎/索引格式版本、文本提取配置、匹配策略及绑定状态。身份不能只依赖文件名或路径。
- 内容指纹应在导入或既有读取阶段计算并保存，避免每次查询为验证缓存再读完整文件。
- 正确恢复顺序：先校验双方身份和配置，再读取对应判定；换答案册、修改内容或策略后立即失效。损坏或不完整缓存重新构建。
- 按磁盘容量预算淘汰最近较少使用的记录；只加载当前需要的数据进内存。
- 在用户明确打开一组书籍、首屏完成且设备空闲后，可准备该组合；预热可取消，不遍历整个书库。预热是在移动等待时间，不等于减少总计算量。

交付：重启后缓存命中与失效测试；分别记录缓存命中耗时、未命中耗时和磁盘占用。

## 4. 内存专项：先归因，再设下降目标

保持主进程与专属 WebView 渲染进程 PSS 的统计口径，并分别观察主上下文与各 Worker 的 JS 堆、外部缓冲区和图形占用。PSS 会按比例计入跨进程共享页面，不能以单一 JS 堆读数代表全应用内存。[Android 内存管理说明](https://developer.android.com/topic/performance/memory-overview)

实施顺序：

1. 在相同书籍、页面和缩放下，记录打开前、恢复两书后、首次查询后、连续翻页后、切换书籍并释放后的内存。
2. 分清 PDF 页面/图像缓存、全文和索引、临时评分特征、后台答案文档句柄分别由谁保留。
3. 验证 _answerHandles 和 _releaseAnswerHandles 的实际调用时机；按引用关系回收无人使用的后台答案实例，不能销毁仍用于阅读或匹配的文档。
4. 为页面、全文和索引缓存设容量预算；限额随设备能力调整。已存在的页面缓存和回收逻辑先核对，避免新增第二套重复缓存。
5. 匹配临时数据按批释放；若增加长期特征缓存，应有字节估算、容量上限及失效机制。字节预算不是 JS 实际堆占用的精确保证，仍需真机测量。
6. Worker 不长期保留主线程的完整数据副本；保留同一底层 PDF 对象的引用不等于复制，但序列化消息、重复加载和缓冲区复制需要实际计量。

首轮门槛是“没有引入无界缓存或持续增长，资源确实可释放”。等归因后再为可控部分设下降目标；现有证据不足以承诺把约 440 MiB 压到某个固定数值。PSS 未立刻下降也不单独证明引用泄漏，应结合对象保留情况与重复操作趋势判断。

## 5. 建议验收目标和测试方法

以下数值是建议的工程目标，均未实现或验证。适用于同一平板、同一组 2023 有书签资料，不外推到扫描件或无书签材料。

| 指标 | 建议目标 |
|---|---|
| 书籍已恢复、准备缓存未命中的首次查询 | 首轮中位数不高于 5 秒；进一步目标为 3 秒 |
| 配对验证独立计时 | 首轮中位数不高于 1 秒 |
| 已准备后的查询 | 30 次以上样本的 p95 不高于 50 ms |
| 已恢复书籍且持久化准备缓存有效 | 首次查询目标不高于 1 秒，单独核算应用启动及 PDF 恢复 |
| 匹配引入的主线程任务 | 无超过 50 ms 的任务；状态反馈目标 100 ms 内 |
| 正确性 | 相同输入下题号、页码、分级、拒答原因和并列候选选择一致 |
| 内存 | 有界临时数据和缓存；反复切换后无持续保留无用文档/任务的趋势 |

现有冷查询只有一个主要样本，不能据此得出稳定的冷查询 p95。后续优化验收建议至少 5 次独立进程首次查询，记录全部值、中位数和最慢值；30 次热查询覆盖多个页面。每次标记持久化缓存是否命中，并保持起始页面、缩放、构建类型和设备状态尽量一致。

把端到端时间拆成 PDF 文本提取、索引构建、配对验证、页面匹配、结果显示；另记后台传输和排队时间。不能只优化验证函数就认定 9 秒已经解决。性能计时关闭 CPU Profiler，热点采样单独运行；新增 Worker 需分别采样。

正确性复用现有有答案资料，补充错误年份/答案关联、公式冲突、重复题号及分数并列、乱码、无书签、扫描件、超长答案、取消后换书等针对性用例。无书签和扫描件另报耗时及拒答/OCR 行为，不能拿有书签结果代替。连续阅读与反复切换至少覆盖一轮 30 分钟观察，仍不宣称证明了所有长期内存行为。

为每个阶段保留独立提交和性能记录。相对于原行为有未解释的匹配差异时，不把优化当作完成。

## 6. C++ 的启动条件与范围

前两项完成后，只有在目标仍未达到、且新的真机 profile 表明剩余成本仍集中于纯评分计算时，才开发局部对照原型。如果剩余成本主要来自 PDF 解码、数据复制、渲染或缓存恢复，应继续优化相应位置。

原型范围优先限定为批量文本特征/评分。序列对齐只有在无书签资料的实际 profile 显示它是热点后才纳入。应用的 PDF 阅读、UI、业务状态和现有判定规则先保留。

- 使用批量接口，计入 WebView 与 Android 桥接、序列化、JNI 调用及内存复制成本；不为每一对字符串调用一次原生代码。
- 明确 UTF-16/Unicode、大小写、正则、空值、浮点计算顺序和同分策略；逐项做差分。
- 以应用端到端时间、峰值及稳态 PSS、安装包体积、兼容性和维护成本决定保留与否。
- 可把“相对已优化 JS，端到端额外改善至少约 30%，并且内存无明显回退”作为原型值得合入的讨论门槛。这是决策建议，不是对 C++ 收益的预测。
- 当前应用仍依赖 WebView 阅读和 UI，单独把匹配引擎改成 C++ 不会消除整个 WebView 运行环境的成本。

## 7. 可按顺序执行的改动包

1. 补充分阶段计时，保留旧结果作为差分参照；实现分批特征复用。
2. 接通后台配对准备，加入任务复用、取消、结果版本检查和回收。
3. 用同一资料验收前两包，定位剩余时间；按结果决定持久化索引和预热的投入。
4. 独立完成内存归因与生命周期修正，确认新增 Worker 和缓存没有反向增加负担。
5. 未达目标且剩余热点符合条件时，进行局部 C++ 原型比较。

实现位置以已测试版本及现有索引为导航依据：独立引擎 HEAD 为 931792f2217a7bb351e3794f27e590c494f68cae；Android 的 showAnswersForPage 索引本轮提示已过期。因此应用集成部分是针对已审阅行为的方案，正式编码前需刷新实际目标文件索引并核对调用与回收位置。原方案不要求重测仅动画变更的版本，也不把旧索引当作当前源码的完整证明。
