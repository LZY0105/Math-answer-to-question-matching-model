# 对页 Android 匹配引擎性能实测

测试日期：2026-09-13。结论仅适用于 **21:25:35 安装的 1.4.0 调试包**。

**结论：有必要优化首次配对准备及其主线程阻塞；本次有书签使用路径不支持为热查询速度而全面重写 C++。内存数据也不足以证明全面原生化能显著节省整个应用的占用。**

## 2. 测量方法

通过平板 WebView 调试接口触发真实“对答案”按钮，在应用内以 performance.now 记录点击到答案面板从加载态变为结果态的时间。计时不包含电脑到设备的调试往返。面板 DOM 更新并非完整 PDF 绘制完成。

先测已打开书籍的热查询，再停止并重启应用，保留原有文档与持久化数据，测新进程第一次查询。没有清空用户数据或磁盘缓存，因此“冷”指新进程中的首次查询，并非首次安装、首次导入或无文件缓存的运行。

另一次新进程查询单独使用 CPU Profiler。该次耗时只作辅助，避免将采样开销混入主要延迟结论。使用 dumpsys meminfo 分别读取主进程与该应用专属 WebView 渲染进程，合计 PSS；未把 RSS 相加当作物理内存。

## 3. 查询实测

| 场景 | 样本 | 结果 |
|---|---:|---:|
| 已打开书籍，第 14 页首次观察 | 1 次 | 19.0 ms |
| 同页重复查询 | 10 次 | 7.2–22.9 ms，中位数 9.05 ms |
| 第 14、20、50、100、200 页，已准备状态 | 5 页 | 19.8、18.7、16.5、16.2、17.1 ms |
| 重启后第一次查询，实际第 20 页 | 1 次 | **9048.9 ms** |
| 上述首次查询中的最长主线程长任务 | 1 次 | **4905 ms** |
| 单独 CPU 采样运行，实际第 17 页 | 1 次 | 8640.4 ms，含采样开销，不作为独立速度提升证据 |

十次重复查询均显示两条“匹配可靠”。五个不同页码分别显示 2、3、2、2、2 条“匹配可靠”。第 17 页采样运行中，1.15 题因 FORMULA_CONFLICT 显示“请核对后使用”，1.16 题显示“匹配可靠”。

以上记录的是应用给出的结果分级及题号/页面定位，**不是逐题人工验算或全书准确率验证**。样本量不足以给出稳定的端侧 p95/p99，报告使用范围和中位数。

## 4. CPU 热点

采样共 24,108 个样本。记录窗口约 30.77 秒，其中约 24.56 秒为空闲；以下比例以约 6.21 秒非空闲采样时间为分母，包含程序运行及垃圾回收等，不能与端到端耗时直接等同。

| 调用链或函数 | 采样归因时间 | 非空闲采样占比 |
|---|---:|---:|
| verifyPair 调用链 | 4501 ms | 72.5% |
| contentAnchorAgreement 调用链 | 4489 ms | 72.3% |
| contentSimilarity 调用链 | 4479 ms | 72.1% |
| bigrams 自身 | 1500 ms | 24.1% |
| normalizeForMatch 调用链 | 1548 ms | 24.9% |

调用链时间存在嵌套，**不能相加**。

已核对压缩函数：ff=verifyPair，df=contentAnchorAgreement，Md=contentSimilarity，Td=bigrams，wd=normalizeForMatch，xd=symbolContexts，Od=extractMathFragments，Ed=similarity。

实际实现会将抽样题目与全部非空答案候选逐个比较，每次重复进行标准化、二元组构造、数学片段提取与符号上下文构造。这与约 4.9 秒的界面主线程阻塞相吻合。

应用已经缓存文档索引、目录对齐与配对判定。此前独立引擎反复调用 preparePair 的桌面耗时，不能当作此应用每次点击都要付出的成本。

## 5. 内存观察

单位 MiB，数值为时点读数，不是峰值。

| 同一运行阶段中的前后对照 | 主进程 + WebView 渲染进程 PSS |
|---|---:|
| 已打开两本书，重复查询前 | 443.6 |
| 十次重复查询后 | 432.4 |
| 新进程恢复两本书，首次查询前 | 355.5 |
| 新进程首次查询后 | 442.9 |
| 另一次运行完成 CPU 采样与五页查询后 | 485.7 |

主 WebView 上下文的已用 JS 堆：
- 十次热查询前后：8.59 → 8.68 MiB。
- 新进程首次查询前后：2.53 → 5.21 MiB。

热查询的十次样本没有显示持续上升的总 PSS，但不足以排除长期泄漏。不同进程运行之间、不同阅读页之间的数值不能直接作为泄漏曲线。

总 PSS 包含图形、PDF 渲染及缓存、代码、文本和索引等；主上下文 JS 堆不包含整个应用、全部 worker 或全部外部缓冲区。**不能把约 400–500 MiB 的两进程总占用全部归给匹配引擎，也不能以 JS 堆较小推断其所有关联内存都很小。**

## 6. 对 C++ 重写的建议

1. **先解决首次准备阻塞界面。** 将配对验证和批量评分放到后台 Worker，UI 线程只处理进度与结果。此举主要改善响应性，不保证同比缩短总时间。
2. **减少重复计算。** 对有效候选复用标准化文本、二元组、数学片段和符号上下文；采用有容量限制、可失效的特征缓存。保留配对身份检查与拒答规则，不能靠跳过验证来获得“加速”。
3. **单独优化 PDF 与缓存生命周期。** 本轮总内存不能分解为匹配算法的独占内存；需要继续跟踪全文、PDF 页面、worker 缓冲区与缓存保留量。
4. **优化后再做局部 C++ 对照原型。** 若目标平板的首次准备仍不能满足产品要求，可以比较批量特征评分与序列对齐内核的原生实现。采用批量接口，并对 JS/C++ 的 Unicode 处理、阈值、并列选择和拒答结果进行差分验证。

现阶段的优先投入是“首次验证的特征复用 + 后台执行”，全面重写的必要性尚未得到实测支持。
